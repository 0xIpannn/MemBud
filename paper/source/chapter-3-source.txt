[002] <Heading2> 3.1 Thinking Framework
[003] This study follows a design-and-evaluate approach: it builds a verification artifact, MemBud, and tests it in a controlled, paired experiment on fixed memory-update cases. The reasoning runs in five linked steps (Figure 3.1).
[004] <ListParagraph> Problem. An LLM memory agent proposes write, revise, and delete operations, and a wrong operation becomes persistent state. Three error types are tracked: omission of required information, corruption of valid prior records, and unsupported additions (Chen et al., 2026; Yang et al., 2026).
[005] <ListParagraph> Gap. Transition-level verification already exists, but prior verifiers read a textual view of the memory before and after the update. It is untested whether an explicit graph of records, claims, evidence, and operations lets a verifier catch errors that a text verifier given the same information would miss.
[006] <ListParagraph> Intervention. MemBud sits between a host memory system and its persistent write. It converts each proposed update into a canonical transition package, verifies it for coverage, preservation, and faithfulness, and returns ACCEPT or HOLD before anything is committed.
[007] <ListParagraph> Controlled test. The same frozen transition is judged by an unguarded pipeline, a text verifier, and a graph verifier, so that any difference is attributable to the verifier and not to the input.
[008] <ListParagraph> Evidence. Results are reported as transition-level error rates, valid-update acceptance, latency, and token cost, with a negative or mixed result treated as a valid outcome.
[009] Figure 3.1. Thinking framework: problem, gap, intervention, controlled test, evidence.

[023] <Heading3> Research flow
[024] The work proceeds through seven phases with two explicit gates, shown in Figure 3.2. Phase 1 reviews the literature and fixes the research questions. Phase 2 constructs and annotates the transition cases. Phase 3 implements the prototype. Phase 4 runs development experiments on the development split only. Gate A freezes the case manifest, prompts, and decision policy. Phase 5 runs the frozen configuration on held-out cases. Gate B requires that held-out labels were not used to tune anything after Gate A. Phase 6 analyses results by arm, error type, and relational stratum, and Phase 7 reports findings with their limitations.
[025] Figure 3.2. Research flow with the freeze gate (Gate A) and the no-tuning gate (Gate B).
[026] <Heading2> 3.2 Research Methods
[027] The methods are organised as the usual data-science pipeline, adapted to a verification study: data collection, exploratory data analysis, preprocessing, splitting, modelling, experimental conditions, and evaluation. There is no model training; the "model" is a rule-based and LLM-assisted verifier, so the modelling step describes its design instead of a fitting procedure.
[028] <Heading3> 3.2.1 Data Collection
[029] The primary dataset is a set of hand-authored synthetic transition cases, because the study needs ground truth that public benchmarks do not provide. A transition case is one frozen package: the prior memory state, the source evidence, one proposed resulting state, the claims that must survive, and the proposed operations (WRITE, REVISE, DELETE, SUPERSEDE, NOOP). Gold labels are stored in a separate file that verifiers never read.

[050] HaluMem is not the primary dataset for three reasons found when its repository and dataset card were reviewed. Its released labels classify a memory system's output as correct, hallucinated, or omitted update, and are produced by an LLM evaluator, so they are not per-claim human labels. It does not provide MemBud's required claims, operation authorizations, or corruption labels for unrelated prior records. Its licence, CC BY-NC-ND 4.0, forbids sharing adapted material, so derived transitions cannot be published with the study. HaluMem therefore informs the error taxonomy, and any use of it as an external check would need a separate, documented mapping from its dialogue and reference-memory fields to fixed transitions. LoCoMo (Maharana et al., 2024) is a candidate only for downstream question answering and is not used in the core experiment.
[051] The v2 set covers 18 case categories with two cases each, split evenly between development and held-out:
[052] <ListParagraph> Valid updates (7 categories, 14 cases): write, revise, supersede, authorised delete, no-op, multi-operation, and contradiction-backed correction.
[053] <ListParagraph> Faulty updates (6 categories, 12 cases): omission, corruption without evidence, corruption with insufficient evidence, unsupported addition, unsupported provenance, and unresolved contradiction.
[054] <ListParagraph> Invalid inputs (5 categories, 10 cases): delete without structured authorisation, authorisation pointing at the wrong target, and undeclared insertion, modification, or removal. These test the input schema, not the verifier.
[055] Proposed updates are authored once and reused unchanged by every arm, so proposal generation never differs between conditions. Because the cases are synthetic and contain no personal data, they can be sent to a hosted LLM API without privacy risk. Cases were authored by the project team and labelled under written annotation guidelines; a second independent review is planned (Section 3.2.7).

[084] The cases contain 30 operations: 11 REVISE, 9 WRITE, 6 NOOP, 2 SUPERSEDE, and 2 DELETE. Twenty-four cases carry a single operation and two carry three. Only 4 of the 26 cases include an evidence item that contradicts a claim, so contradiction handling is exercised in a small minority of cases.
[085] These statistics lead to a design decision. With about two prior records and one evidence item per case, a text verifier can see the whole transition at once, and long provenance chains, cross-record entity conflicts, and temporal ordering are essentially absent. A graph is therefore unlikely to show an advantage on this set, and the study adds a separate relational stratum of cases built to need such structure (Section 3.2.6). The same analysis will be repeated on the independent fresh set, together with claims per record and the share of cases whose gold decision depends on more than one evidence item.
[086] If HaluMem is later used for an external check, the exploratory step would additionally count its update memory points (is_update), memory types, and the number of original memories each update replaces, and would record which fields can map to MemBud's required claims and evidence.
[087] <Heading3> 3.2.3 Data Preprocessing
[088] Preprocessing turns a raw case into a validated transition package and then into two renderings of identical content, one graph and one text (Figure 3.3). Nothing is imputed: if a source, timestamp, or authorisation is absent, it stays absent and is never invented.
[089] <ListParagraph> Parse. The case is read into typed objects: records (an ID and a list of atomic claims), evidence items (ID, source, original text, supported claims, optional contradicted claims), required claims, and operations.
[090] <ListParagraph> Normalise. Operation names are upper-cased. Legacy input that uses a supersedes field is converted to explicit REVISE or SUPERSEDE operations. Input without a schema_version is treated as frozen version 1 and keeps its weaker rules; all new cases use version 2.
[091] <ListParagraph> Validate. Record, claim, and evidence identifiers must be non-empty and unique. Each operation must reference real records: WRITE creates a new record, REVISE keeps the record ID and must change it, SUPERSEDE needs a distinct replacement, and DELETE needs a reason plus a structured authorisation (source, evidence_id, target_id, rationale) whose evidence exists and whose target matches. NOOP must be the only operation and leave the state unchanged.
[092] <ListParagraph> Check operation coverage (version 2). Every actual state change must be declared by exactly the matching operation: an added record needs WRITE or SUPERSEDE, a changed record needs REVISE, and a removed record needs DELETE or SUPERSEDE. A prior record can be targeted once, and a candidate record proposed once.
[093] <ListParagraph> Route failures. A case that breaks any rule above is recorded as INVALID_INPUT for every arm, is never verified, and never writes memory. It is excluded from detection metrics and reported in its own block.
[094] <ListParagraph> Render. From the same validated object the system builds (a) the canonical graph described in Section 3.2.5 and (b) a deterministic compact text serialisation containing every field, with provenance, in fixed order.
[095] <ListParagraph> Reconcile with the store. Before verification the persisted store must equal the transition's prior state, otherwise the run stops and writes an audit error.
[096] Figure 3.3. Preprocessing pipeline from raw case to validated transition package, graph rendering, and text rendering, with the INVALID_INPUT exit.
[097] Claims are compared as exact strings, so the pipeline does not infer that two differently worded claims mean the same thing. Paraphrase and contradiction judgments are handled only by a separate, optional semantic verifier (Section 3.2.5). Case and label files are fixed by SHA-256 hashes recorded in a manifest, so any later change to the data is detectable.
[098] <Heading3> 3.2.4 Data Splitting
[099] The 36 v2 cases are divided into 18 development and 18 held-out cases by stratification on case class, so that each split has 7 valid, 6 faulty, and 5 invalid-input cases. A random split is not used because each case is authored individually and the classes are deliberately balanced, so a random draw could leave a fault type out of one split.
[100] The development split is used to build and debug the verifiers and to tune the LLM prompt. The held-out split is used only to report results. The 36 cases were authored together and frozen before the first v2 run, and the cases and labels are pinned by hash. Labels live in a separate file and never appear in verifier input or prompts.
[101] One limitation must be stated plainly. After the first held-out LLM run, the held-out cases were used to diagnose four false holds and to choose a clarified prompt (version 2). The prompt was then replicated on the 13 schema-valid development cases that had not been used for that diagnosis. Held-out numbers for the LLM arms are therefore development evidence, and the development replication is the only out-of-sample check so far. The deterministic verifiers have no tuned parameters and are unaffected.
[102] To close this gap, the final evaluation uses a third, untouched split: an independent fresh set (Figure 3.4). It is frozen at Gate A, before any run on it, and sized from the precision it must deliver. If a verifier makes no false accept on n faulty cases, the exact 95% upper bound on its false-accept rate is 1 − 0.05^(1/n), which is about 9.5% for 30 cases and 5.8% for 50. The target is therefore at least 50 gold-faulty and 50 gold-valid cases, and results on smaller sets are reported as exploratory with interval estimates, not significance tests.
[103] Figure 3.4. Data splits over time: development (tuning allowed), held-out v2 (consumed for prompt selection), and the fresh set (frozen at Gate A, never used for tuning).
[104] <Heading3> 3.2.5 Modelling: The MemBud Method
[105] MemBud is a pre-commit safety layer: it receives a proposed memory update from a host system, verifies it, and allows the host to write only if the update passes (Figure 3.5). It does not replace the host's memory architecture, and the host does not need to store data as a graph. A backend adapter converts host records into the canonical form and carries the decision back.
[106] Figure 3.5. MemBud architecture: host proposes, adapter builds the transition package, graph and text renderings feed their verifiers, the decision policy returns ACCEPT or HOLD, only ACCEPT reaches the store, and every step is audited.
[107] Formal definition. A transition is a tuple T = (B, C, E, R, O). B is the set of prior records and C the proposed resulting records, each record holding a set of atomic claims cl(·). E is the set of evidence items, each with supported claims and optional contradicted claims. R is the set of required claims and O the set of operations. Write S for the union of all supported claims and X for the union of all contradicted claims.
[108] Canonical graph. From T the system builds a directed graph G with the node and edge types below (Figure 3.6). Claim nodes are shared, so the same claim in a prior record, a candidate record, and an evidence item is one node, and provenance becomes a path.

[156] Verification checks. Three checks, taken from the transition-verification criteria of Yang et al. (2026), are computed on every transition. The graph verifier derives them from graph adjacency; the text verifier derives them from claim sets.
[157] <Code> \begin{aligned}\mathrm{Cov}(T) &= \bigl[\, R \subseteq \textstyle\bigcup_{c \in C} \mathrm{cl}(c) \,\bigr] \\\mathrm{Pres}(T) &= \bigwedge_{b \in B,\ \mathrm{op}(b) \neq \mathrm{DELETE}} \bigl[\, \mathrm{cl}(b) \subseteq \mathrm{cl}(c_b) \ \lor\ (\mathrm{op}(b) \in \{\mathrm{REVISE}, \mathrm{SUPERSEDE}\} \ \land\ A_b \neq \varnothing \ \land\ A_b \subseteq S) \,\bigr] \\\mathrm{Faith}(T) &= \bigl[\, U = \varnothing \,\bigr] \ \land\ \bigl[\, \mathrm{cl}(C) \cap X = \varnothing \,\bigr] \ \land\ \mathrm{Connected}(G)\end{aligned}
[158] Here c_b is the candidate record that replaces b (the same ID, or the SUPERSEDE replacement), and A_b = cl(c_b) \ cl(b) is the set of claims it adds. The evidence-backed alternative applies only to the target of a REVISE or SUPERSEDE; if b has no operation and no candidate record, Pres fails. U = cl(C) \ cl(B) \ S is the set of candidate claims that are neither prior nor supported. Connected(G) requires every node to be reachable from the transition node and every declared operation to have its target, proposal, and authorisation edges, so a malformed or tampered graph fails faithfulness with a distinct reason code.
[159] In words: coverage fails when a required claim is missing from the candidate state; preservation fails when a prior record is changed or removed without a matching operation, or is changed in a way the evidence does not support; faithfulness fails when a new claim has no evidence path, is contradicted by evidence, or the graph is structurally inconsistent. Each check returns PASS, FAIL, or UNCERTAIN with a machine-readable reason code (for example REQUIRED_CLAIM_OMITTED, PRIOR_RECORD_UNAUTHORIZED_CHANGE, UNSUPPORTED_CLAIM, CONTRADICTED_CLAIM) and the IDs affected.
[160] Decision policy. One policy serves every guarded arm: the update is committed only if all required checks pass.
[161] <Code> D(T) = \begin{cases} \mathrm{ACCEPT} & \text{if } \mathrm{Cov}(T) \land \mathrm{Pres}(T) \land \mathrm{Faith}(T) \\ \mathrm{HOLD} & \text{otherwise, including UNCERTAIN or a malformed verifier response} \end{cases}
[162] HOLD is the safe default, a transient retry of a model call can never authorise a commit, and an invalid input is reported as INVALID_INPUT before verification. A held update changes nothing in the host, so no rollback is needed. A REVISE decision (asking the host to regenerate the operation with verifier feedback) is not implemented in the current prototype and is not part of the primary comparison, because it changes the proposal and breaks the paired design; it is left as a separate extension.
[163] LLM-assisted verifier. Exact-claim rules cannot judge meaning, so an optional LLM verifier evaluates the same three checks. The graph and text arms share one prompt policy, JSON output schema, model, temperature, and retry setting; only the serialisation of the transition differs, graph nodes and edges versus compact text. The model is accessed through DeepSeek's OpenAI-compatible API (model ID deepseek-flash, temperature 0, JSON mode, prompt version membud-transition-checks-v2). Responses are validated against the allowed statuses and reason codes, and a malformed or unavailable response becomes UNCERTAIN and therefore HOLD. Completions are cached in SQLite by provider, model, prompt, and settings, so a rerun costs no tokens. Each run logs the returned model name, token usage, retries, cache hits, and latency. A model alias may not identify an immutable backend revision, so the run date is recorded too.
[164] Semantic comparison. An optional, separate module compares claims for paraphrase equivalence and contradiction with the same model and adds a fourth, semantic check. It never alters the deterministic baseline and fails closed to UNCERTAIN.
[165] Commit protocol. Accepted state is kept in a versioned JSON store. Before verification, the stored records must equal the transition's prior state. The decision is appended to an append-only audit log, and only on ACCEPT is the candidate state written atomically (temporary file in the same directory, fsync, rename) with the version incremented once. An optional expected_version gives optimistic concurrency control, and a POSIX file lock covers the load, verify, write, and audit section. HOLD never creates or rewrites the store (Figure 3.7). Each audit entry records the run ID, UTC start time, elapsed time, store version before and after, and an optional code revision.
[166] Figure 3.7. Sequence of a guarded update: host proposal, adapter snapshot, verification, audit append, and a store write that occurs only on ACCEPT.
[167] Adapter contract and backends (RQ2). An adapter provides snapshot(scope), which returns canonical records, and replace_state(scope, records), which atomically replaces the whole scoped state. It must not call any host mutation before ACCEPT, must re-check a fresh snapshot or use a backend transaction to avoid stale writes, and must document what its mapping loses (provenance, timestamps, relations). Three levels of backend evidence are used:
[168] <ListParagraph> Reference backend (in-memory and SQLite). It demonstrates the full intercept, verify, and commit path, with byte-identical state after HOLD.
[169] <ListParagraph> Staged-proposal bridge for a Mem0-style extractor. Extracted proposals plus a prior snapshot become a version 2 transition, tested without importing Mem0.
[170] <ListParagraph> Feasibility assessment of Mem0 and A-Mem write paths. Inspection of Mem0 (mem0ai 2.2.1) found no safe public pre-commit hook, and A-Mem's note evolution can rewrite neighbouring notes, so guarding either needs a staged write or a fork.
[171] No third-party compatibility is therefore claimed. RQ2 is answered by the contract, the reference backend, and a documented account of what each host would need to supply and lose; a live Mem0 or A-Mem integration is a stated extension. A localhost HTTP sidecar and an agent-runtime hook were also built as a feasibility spike for intercepting an agent's memory-tool write; they are not part of the evaluation.
[172] <Code> Algorithm 3.1  Verify-and-commitInput:  raw transition x, store s, representation r in {graph, text}, verifier V1  T <- parse_and_validate(x)               # schema version 2 invariants2  if invalid: return INVALID_INPUT          # no verification, no write3  if records(s) != T.before: fail closed and log an audit error4  G <- build_graph(T);  Z <- render_text(T) # same facts, two renderings5  result <- V(G) if r = graph else V(Z)     # Cov, Pres, Faith (+ Sem if enabled)6  D <- ACCEPT if every check = PASS else HOLD7  append audit(T, result, D)8  if D = ACCEPT: atomic_write(s, T.candidate, version + 1)9  return D

[197] Why a text-fair control is required. The preliminary fairness audit on the 36 v2 cases showed that the graph verifier differed from the original text baseline on exactly two cases (DEV-13 and HELD-13), both contradiction cases. The original text baseline cannot read the contradicts field, so this difference came from information access, not graph structure. Once the text arm was given the same access (text-fair), it matched the graph verifier on every one of the 36 decisions, and both reached 0 false accepts and 14 of 14 valid updates accepted. On this set, then, no decision-level benefit of graph structure is shown. This result is narrow (36 synthetic, single-reviewer cases written alongside the verifiers), but it fixes the design rule that a graph is only compared with a text verifier that holds the same facts.
[198] Hypotheses. Because of that result, the graph hypothesis is stated for cases where structure could matter.
[199] <ListParagraph> H1 (relational stratum). On cases that need relational structure, the graph arm detects more faulty transitions than text-fair at an equal false-hold rate. H0: no difference.
[200] <ListParagraph> H2 (non-relational cases). On the remaining cases, graph and text-fair agree, replicating the audit.
[201] <ListParagraph> H3 (guard value). Guarded arms cut false accepts relative to unguarded without a large fall in valid-update acceptance.
[202] If H1 is not supported, that result is reported as it stands and the error analysis explains where the graph did and did not help.
[203] Relational stratum (planned). A new case family is built so that detection cannot be read off a single annotation: (a) multi-hop provenance, where a claim is supported only through a chain of two or more links; (b) cross-record entity conflict, where two active records state incompatible values for the same entity and attribute with no contradicts annotation; and (c) temporal ordering, where a revision predates or conflicts with a later-dated prior record. This needs the canonical schema to gain entity, derivation, and valid-time attributes. Any edge that needs semantic judgement, such as entity linking, is produced once by a shared extraction step and given to both arms, as graph edges or as listed relations in text, and its cost is reported for both.
[204] Fairness controls. The text and graph arms get the same prompt effort, tuned on the development split only, and prompts, policy, and model are frozen at Gate A. A parity test asserts that the text rendering and the graph carry the same facts, provenance, and relations for every case. Token counts include the full verifier input, graph construction, and serialisation.
[205] <Heading3> 3.2.7 Model Evaluation
[206] Each case is scored by comparing a verifier's decision with the gold label, and arms are compared case by case on identical inputs (Figure 3.9). Every metric is reported with its numerator and denominator, and a case with no applicable denominator is marked not applicable, never zero.
[207] Figure 3.9. Decision matrix: gold class (valid, faulty, invalid input) against decision (ACCEPT, HOLD, INVALID_INPUT), with the cells that define each metric marked.
[208] Transition-level reliability. Let F be the gold-faulty cases, V the gold-valid cases, and TP the faulty cases held. Precision is TP over all cases held.
[209] <Code> \begin{aligned}\mathrm{Detection} &= \frac{|\{f \in F : D(f) = \mathrm{HOLD}\}|}{|F|}, \qquad \mathrm{FalseAccept} = 1 - \mathrm{Detection} \\\mathrm{ValidAcceptance} &= \frac{|\{v \in V : D(v) = \mathrm{ACCEPT}\}|}{|V|}, \qquad \mathrm{FalseHold} = 1 - \mathrm{ValidAcceptance} \\F_1 &= \frac{2\,\mathrm{Precision}\cdot\mathrm{Detection}}{\mathrm{Precision}+\mathrm{Detection}}\end{aligned}
[210] Detection alone rewards a verifier that holds everything, so the primary comparison metric is F1 for holding faulty transitions, always reported beside the false-hold rate; this choice is fixed before the fresh set is run. Error-type rates complement it: claim omission rate (required supported claims absent from the candidate over all required supported claims), unsupported-addition rate (unsupported material candidate claims over all material candidate claims), and prior-record corruption rate (valid prior records wrongly changed or removed over valid prior records expected to persist). INVALID_INPUT cases are scored in a separate block and excluded from precision and recall, because they test the input schema, not the verifier.
[211] For LLM arms, results are given in two views. The as-completed view excludes rows where the verifier failed to return a valid response. The fail-closed intention-to-treat view counts every such row as a HOLD that earns no detection credit, which is the honest view for a safety layer.
[212] Cost and utility. The study reports graph preparation time and verification time separately, end-to-end latency, input and output tokens, request attempts, retries, cache hits, and decision counts. Dollar cost is reported only as an estimate, because the API returns token counts and not billed amounts; actual spend is confirmed against the provider's billing page. Downstream question-answering accuracy is measured only if a dataset with matching annotations is used, and acceptance of updates is never presented as evidence of QA utility.
[213] Validating the results.
[214] <ListParagraph> Label validity. A second, independent reviewer labels every final case using a blind quiz that contains no gold labels. Agreement is reported as Cohen's kappa, disagreements are adjudicated, and a new manifest version is frozen. Until then all labels are described as single-reviewer and exploratory.
[215] <ListParagraph> Statistics on paired cases. The unit of analysis is the case, not the claim. Differences between arms use an exact McNemar test on discordant pairs and a paired bootstrap 95% interval over cases; single rates use Clopper-Pearson intervals. H1 is supported only if the interval for the graph minus text-fair difference in detection on the relational stratum excludes zero at an equal false-hold rate.
[216] <ListParagraph> No tuning after the freeze. Prompts, policy, and arms are fixed at Gate A, and the fresh set is run once.
[217] <ListParagraph> Error analysis. Every false accept and false hold is reviewed by hand, and reason-code counts are tabulated by arm, case class, operation type, and split.
[218] <ListParagraph> Reproducibility. Manifest hashes, pinned model and prompt versions, the response cache, append-only audit logs, and the code revision make each run replayable; a cache-only rerun must reproduce the same decisions.
[219] <ListParagraph> LLM variance. A small slice is repeated several times at temperature 0 to measure residual nondeterminism, and verifier outputs are never used as labels.

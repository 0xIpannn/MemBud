# 3. Implementation Method

## 3.1 Thinking Framework

MemBud is a pre-commit safety layer for LLM memory agents. A memory agent proposes WRITE, REVISE and DELETE operations, and a wrong operation becomes persistent state; the errors of interest are omission of required information, corruption of valid prior records, and unsupported additions (Chen et al., 2026; Yang et al., 2026). Transition verification already exists for textual views of memory, but it is untested whether an explicit graph of records, claims, evidence and operations detects errors that a text verifier given the same facts would miss. MemBud converts each proposed update into a canonical transition, verifies coverage, preservation and faithfulness, and returns ACCEPT or HOLD before anything is written. The same frozen transition is judged by an unguarded pipeline and by text, text-fair and graph verifiers, so any difference is attributable to the verifier rather than the input; results are reported as transition-level error rates, valid-update acceptance, latency and token cost, with a negative result treated as a valid outcome. RQ1 (reliability) maps to this controlled comparison, RQ2 (modularity) to the adapter contract, and RQ3 (trade-offs) to acceptance and cost.

## 3.2 Research Methods

**Data collection.** The evaluation uses a hand-authored synthetic set of 36 transition cases, because public memory benchmarks do not supply the per-claim labels a transition verifier needs. A case is one frozen package: the prior memory state, evidence with supported and optionally contradicted claims, required claims, one proposed resulting state, and declared operations (WRITE, REVISE, DELETE, SUPERSEDE, NOOP). The set covers 18 categories with two cases each: seven valid-update categories (14 cases), six faulty-update categories (12 cases: omission, corruption without or with insufficient evidence, unsupported addition, unsupported provenance, unresolved contradiction), and five invalid-input families (10 cases: deletion without structured authorisation and undeclared insertion, modification or removal). The 36 cases are split 18 development / 18 held-out (7 valid, 6 faulty, 5 invalid each) and were frozen before any version-2 run. Labels are stored separately and never enter verifier input or prompts; they are single-reviewer exploratory annotations, and an independent second review is pending. Cases and labels are SHA-256 pinned, and no licensed benchmark data is used.

**Preprocessing.** Preprocessing performs no imputation or feature engineering. Each case is parsed into typed records, evidence items, required claims and operations, normalised to explicit operations (legacy supersedes notation becomes REVISE or SUPERSEDE), and validated under schema version 2. Every actual state change must be declared by exactly the matching operation; a prior record and a candidate record may each be targeted once; DELETE requires structured authorisation (source, evidence_id, target_id, rationale) whose evidence exists and whose target matches; and NOOP must leave the state unchanged. A case that breaks any invariant is recorded as INVALID_INPUT for every arm, rejected before verification, and never writes memory. From the validated transition T = (B, C, E, R, O) the system derives two renderings of identical content: a canonical graph G with transition, record, claim, evidence and operation nodes and typed edges, and a deterministic compact text serialisation Z. Claims are compared as exact strings; paraphrase and contradiction judgements belong to the optional semantic module.

**Verifier configurations.** Every guarded arm uses one decision policy: ACCEPT only if coverage, preservation and faithfulness all pass; any FAIL or UNCERTAIN yields HOLD; schema-invalid input is INVALID_INPUT before verification. Table 1 lists the arms. Text-fair exists because the original text baseline does not read evidence.contradicts; giving it the same annotation access as the graph makes it an information-parity control, so a graph-versus-text comparison does not confound representation with annotation access. An optional LLM verifier applies the same three checks to graph or text serialisations with one model, prompt policy, temperature and output schema; a separate semantic comparator adds a fourth check and fails closed to UNCERTAIN.

Table 1. Rule-based experimental arms.

| Arm | Verifier | Contradiction access |
|---|---|---|
| Unguarded | Applies the candidate unchanged | No |
| Text | Exact claim-set checks | No |
| Text-fair | Claim sets + contradiction access | Yes (control) |

**Adapter and backends.** An adapter provides snapshot(scope) and an atomic replace_state(scope, records); it must not mutate the host before ACCEPT and must document the provenance, timestamps and relations its mapping loses. A reference backend (in-memory and SQLite) demonstrates the full intercept, verify and commit path, with byte-identical state after HOLD. Mem0 2.2.1 and A-Mem were source-inspected for a safe pre-commit boundary; neither exposes one, so no third-party compatibility is claimed and a staged or forked integration remains future work.

**Evaluation protocol.** The unit is the case, paired across arms. For expected-faulty cases F and expected-valid cases V we report detection (faulty held / |F|), false-accept rate (1 - detection), valid acceptance, false-hold rate, and F1 for holding faulty transitions; error-type rates use claim- and record-slot denominators. INVALID_INPUT cases are scored in a separate block and excluded from precision and recall. LLM arms are reported as-completed and as fail-closed intention-to-treat, where an execution error is a non-accepting HOLD that earns no detection credit. Paired differences are reported with case identifiers, and two contrasts are pre-specified: text versus text-fair (the value of contradiction access) and text-fair versus graph (representation with information held equal). At n = 36 single-reviewer synthetic cases the analysis is descriptive: no significance or power claim is made, and a zero difference is read as not detectable at this size, not as equivalence. A larger fresh set with independent annotation, exact intervals and a paired test is planned; cost, tokens and latency are instrumented, and downstream question-answering utility is not measured.

**Threats.** Cases were authored alongside the verifiers, labels are single-reviewer, n is small, claims are matched as exact strings, and LLM arms differ in token and latency budget. The independent fresh set and the second review address these limitations and are not yet collected.

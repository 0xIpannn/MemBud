# Reference: code layout, schema and input semantics

## Code layout

- `membud.schemas`: canonical records, evidence, operations, transitions, checks, and validation.
- `membud.graph`: canonical graph construction and Mermaid rendering.
- `membud.serialization`: lossless dictionary and deterministic text representations.
- `membud.migrations`: explicit format versioning and migration policy (`migrate_transition_to_v2`, `transition_needs_migration`, `store_needs_migration`); the normative policy is `docs/format-policy.md`.
- `membud.verification`: dispatches structural graph verification or the exact-claim-set text baseline, plus the optional LLM-assisted path. Checks return `PASS`, `FAIL`, or `UNCERTAIN` statuses with machine-readable reason codes and affected IDs.
- `membud.graph_verification`: structural verifier that derives coverage/preservation/faithfulness from graph adjacency (evidence-to-claim provenance paths, required-claim reachability, `REVISES`/`DELETES`/`SUPERSEDES` operation edges, `CONTRADICTS` edges, orphan/disconnected claim nodes, and operation/authorization edge consistency).
- `membud.semantic`: optional, separate semantic comparison mechanism (paraphrase equivalence and contradictions) with fail-safe `UNCERTAIN`; it never changes the deterministic baseline and is only used when a caller explicitly requests `verify_with_semantics`.
- `membud.llm`: bounded-retry, JSON-mode OpenAI-compatible chat client with usage/latency capture.
- `membud.store`: guarded, versioned JSON persistence and append-only audit logging. Accepted state is stored as `{"schema_version": 2, "version": <int>, "records": [...]}`; legacy bare-list stores load as v1 and migrate on the next `ACCEPT`. Each `ACCEPT` increments the version exactly once, while `HOLD` never creates or rewrites the store. A transition is verified only when the persisted store's records and claims match the transition's `before` state; otherwise the run fails closed and records an audit error. Commits reject `ACCEPT` results unless the three required checks (coverage, preservation, faithfulness) are present, pass, and carry a consistent `passed` flag; optional `semantic` and `transcript_grounding` checks are accepted and must also pass. Writes are atomic (same-directory temp file, fsync, rename) and only happen on ACCEPT; on ACCEPT the state file is written first, the completed audit event is appended after it, and a caught append failure rolls the write back (a process death in that gap can leave an accepted state without a completed audit event — the documented crash window, not a write-ahead guarantee). Error events record `store_written`/`rolled_back`. Stray temp files are cleaned and never read as state. An optional `expected_version` gives optimistic concurrency control, and a POSIX `flock` on `<store>.lock` serializes the guarded load/verify/write/audit critical section. Locking caveats: by default (`require_lock=False`), if `fcntl` is unavailable or the lock file cannot be opened/flocked, `run_case` degrades to unlocked execution and logs `lock_acquired: false` (pass `require_lock=True` to fail closed instead); the exclusive lock is held across the entire critical section including any caller-supplied verifier callback (such as an LLM call), so pass `lock_timeout_seconds` to bound contention. Callers must pass the result from the selected verifier; the store validates result structure but does not independently rerun an external LLM verifier. Audit entries include run ID, UTC start time, elapsed time, store schema/version before and after, lock status, expected version, and optional caller-supplied code revision.
- `membud.conversation`: canonical conversation transcripts, multi-format parsers (`membud`, `openai`, `opencode`, `halumem`, `text`), transcript-grounded evidence verification (`verify_transcript_grounding`, `verify_with_transcript`), `RuleBasedConversationExtractor`, `LLMConversationExtractor`, `run_conversation_session`, and CLI.
- `membud.demo`: bundled fixtures and the local demonstration runner.
- `membud.experiment`: paired unguarded/graph/text development pilot runner.
- `membud.metrics`: explicit-denominator metrics for a hash-pinned manifest run.
- `membud.checkpoint`: append-only JSONL run checkpoints with a config fingerprint and crash-tolerant resume (`--resume`).
- `membud.cost`: token-class cost estimates with explicit pricing provenance; never a billed amount.
- `membud.migrations`: explicit format versioning/migration policy; normative doc: `docs/format-policy.md`.
- `membud.adapters`: structural adapter contract for host memory backends. `membud.adapters.mem0_bridge` adds a host-owned staged-proposal bridge for a Mem0-style extractor (no Mem0 import, no Mem0 compatibility claim).
- `membud.service`: localhost-only, stdlib `/verify` sidecar exposing the deterministic verifier over loopback; it persists nothing and fails closed.
- `integrations/opencode/`: Phase 0 opencode `tool.execute.before` guard plugin, mock memory tool, node/bun harness, config snippet, and measured latency caveats.

`membud.core` is a compatibility facade that re-exports the public API. New code should import from the focused modules directly.

## Schema and compatibility

The canonical transition is represented by `Transition`, `Record`, `Evidence`, `DeletionAuthorization`, and `Operation` in `membud.schemas`. `transition_dict()` emits the normalized JSON form: `schema_version`, `case_id`, `before`, `candidate`, `evidence`, `required_claims`, and `operations`. Legacy input using `supersedes` is accepted and normalized to explicit operations; serialized output uses `operations` only.

The serialized transition format is now versioned (`schema_version: 2`). Version 1 input without an explicit `schema_version` remains loadable for frozen archival data and keeps the legacy, weaker operation semantics; version-2 input enforces the strict operation invariants described below. Version-less input is still read as frozen v1 archival data (equivalent to explicit `schema_version: 1`), but the **commit path** (`store.run_case`/`store.commit`) refuses legacy transitions unless an explicit `allow_legacy=True` archival replay is requested; new transitions must declare `schema_version: 2`. `schema_version` must be a JSON integer — booleans, floats and strings are rejected instead of being reinterpreted. Archival v1 transitions **round-trip as v1** (no silent upgrade): callers who want the current format call `membud.migrations.migrate_transition_to_v2()`, which re-validates under the strict invariants and fails closed on legacy data with undeclared changes. Persisted v1 stores (a bare JSON list) are migrated to the v2 envelope by the next `ACCEPT`, while a `HOLD` leaves them byte-identical; unknown future format versions are rejected. The full version registry, compatibility matrix, release checklist, and explicit non-guarantees are in [`docs/format-policy.md`](format-policy.md); the `membud.core` facade is retained for compatibility, while focused module imports are preferred.

## Input semantics

A transition contains the full prior state (`before`), the full proposed resulting state (`candidate`), explicit source-supported claims (`evidence[].supports`), claims required to survive (`required_claims`), and proposed `operations`. Evidence can also retain a `source` reference and original `text` excerpt. **Evidence trust boundary:** standalone transition verification (`membud.verification.verify`, `membud.store.run_case`, or `/verify` without `transcript`) treats `evidence` as caller-declared input — `ACCEPT` proves the candidate and operations are consistent with the supplied `evidence`, not that those evidence items came from a real external source. External provenance binding requires transcript-grounded verification (`membud.conversation.verify_transcript_grounding` / `/verify` with `transcript`) or a host-owned staging adapter that supplies evidence from trusted host records. Claims are compared as exact strings by the deterministic baseline; semantic equivalence is not inferred there. Optional `evidence[].contradicts` declarations add explicit contradiction relationships consumed by graph verification, and the separate `membud.semantic` module can be requested explicitly when semantic comparison is wanted.

Operations use explicit types and record references:

- `WRITE` proposes a new candidate record.
- `REVISE` changes an existing record while retaining its ID.
- `DELETE` removes a prior record and requires both a human-readable `reason` and structured authorization metadata: `authorization: {source, evidence_id, target_id, rationale}`. `evidence_id` must reference transition evidence, `target_id` must match the operation target, and a missing or mismatched authorization is rejected.
- `SUPERSEDE` replaces a prior record with a distinct candidate record.
- `NOOP` must be the only operation, and its candidate state must equal the prior state.

Strict operation invariants (schema version 2): every added candidate record needs a `WRITE` or `SUPERSEDE`; every changed prior record needs a `REVISE` and a `REVISE` must actually change the record; every removed prior record needs a `DELETE` or `SUPERSEDE`; every operation must correspond to a real state change; a prior record can only be targeted once; and a candidate record can only be proposed once. Undeclared insertions, modifications, or removals raise `ValueError` instead of producing a decision. Legacy input with `supersedes` and exactly one candidate record is normalized to these operations; serialized transitions use only `operations`.

Faithfulness allows claims already present in prior memory or explicitly supported by evidence. Preservation requires prior claims to remain on the same record unless an explicit `REVISE` or `SUPERSEDE` supplies evidence for every added replacement claim, or an explicit reasoned `DELETE` removes the record. An operation alone does not make an unsupported revision safe. Omitting an operation does not authorize removal, which lets the fixtures represent accidental omissions as well as intentional changes. Candidate state replaces the store only on `ACCEPT`, and only when the persisted store matches the transition's prior state; held transitions never rewrite the store file.

The rule-based `graph` and `text` paths are now distinct verification strategies over the same transition facts. `text` is the original exact-claim-set baseline; `graph` builds the canonical graph and makes its decisions from graph structure (provenance paths, required-claim reachability, operation edges for changes/removals, `CONTRADICTS` relationships, connectivity, and structural consistency), so it can fail a transition the claim-set baseline accepts (for example, a candidate claim explicitly contradicted by connected evidence). The optional LLM path sends graph or text serialization to the same model and prompt policy. The deterministic verifiers emit pass/fail results; the LLM verifier can also return `UNCERTAIN`. Any failed or uncertain check prevents commit. The fixtures function as their own annotation oracle and are not benchmark evaluation data.

## Demo scenarios and limitations

The bundled cases exercise valid updates (`valid`, `valid-noop`, `preserve-added-claim`, `supported-revision`, `explicit-supersession`, `remove-record`) and unsafe updates (`omission`, `corruption`, `unsupported`, `unsupported-plus-valid`, `required-claim-deletion`). `implicit-removal` is no longer a runnable fixture: undeclared removals are now rejected by schema validation and are covered by unit tests instead. The expected decisions and failing checks for each case are covered by the test suite. These are hand-authored examples, not a representative benchmark. Claims are compared as exact strings; the checks do not infer semantic equivalence, resolve factual conflicts, or establish whether a deletion reason is actually authorized. A successful demo run is not evidence of production readiness or graph-verification effectiveness.
